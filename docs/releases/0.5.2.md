# Cordon 0.5.2

The security audit's fixes, and three defects found by turning on every capability at once.

```
   ┌──────────────────────────────────────────────────────────────────────────┐
   │  Detection rules are unchanged (rulepack 0.2.0). What changed is what    │
   │  reaches them: ClamAV in a large repository, the files of a distroless   │
   │  image, a pre-commit scan beside node_modules, a sandboxed install that  │
   │  can no longer touch its own trace, and archives metered as they inflate.│
   └──────────────────────────────────────────────────────────────────────────┘
```

```
  Map of this release
  ├─ Install ................ pipx · the Action · the containers
  ├─ Breaking ............... CircleCI, Buildkite and Azure name the organisation
  ├─ Fixed .................. what was silently not checked, and is now
  ├─ Hardened ............... the sandbox, archives, git, the feed
  └─ Verify it .............. hashes, signatures, provenance
```

## Install

```
   pipx install cordon-scanner==0.5.2          or, already installed:
   pipx runpip cordon-scanner install --require-hashes -r <your pinned requirements>

   GitHub Action   uses: Threx-code/cordon/action@v0.5.2   (pin the commit SHA the tag names)
   Container       ghcr.io/threx-code/cordon:0.5.2        amd64 and arm64; pin it by digest
   Runner          ghcr.io/threx-code/cordon-runner:0.5.2 new: the scanner with git
   Bitbucket pipe  ghcr.io/threx-code/cordon-bitbucket-pipe:0.5.2
```

## Breaking

```
   CircleCI · Buildkite · Azure      an upload names its organisation:
                                     CORDON_ORGANIZATION=<id>  (or the `organization` parameter)
                                     the exchange asks for audience cordon:<id>

   why     nobody can prove they control one of those accounts, so the cloud bound each to
           the first organisation that claimed it; another company could receive your uploads
   who     GitHub, GitLab, Bitbucket and Jenkins are unchanged
```

## Hardened

```
   the sandbox      the install runs as an unprivileged user with no capabilities; the
                    tracer, the trace, the lookup log and the nonce are root's; a run whose
                    trace does not show the install starting is "not watched", never clean
   archives         decompressed by the scanner and metered as they inflate: ratio, budget,
                    deadline. A 2 MB tar.gz of zeros: refused at under 70 MB (was 2.2 GB)
   zip              a member only the local headers carry is reported, and still scanned
   git (runner)     redirects refused past the allowed hosts
   feed deltas      decompressed with a ceiling
   VS Code          only paths inside the workspace are marked
```
